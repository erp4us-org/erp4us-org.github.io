# Community website and launch checks

## Baseline and changes

- The site uses Astro's static catch-all route, flat English/German catalogs, brand CSS tokens, and GitHub Pages Actions. It used to fetch only a star count. `Layout.astro` now shares navigation, theme controls, and metadata; `ProjectData.astro` renders the different public GitHub views. No app code, runtime API calls or extra service are required.
- The landing page points to contributor onboarding (`/contribute/`), public decisions and governance (`/community/`), activity (`/development/`), evidence-backed milestones (`/roadmap/`) and the devlog (`/devlog/`). All routes have German counterparts.
- Capability copy was reviewed against the application [source revision](https://github.com/erp4us-org/erp4us/tree/832c2fb138996898647520b771437bdc837b120a), its README, roadmap, issue #16 and ADRs 0001–0004. The available capability is local development only. The first cross-service business flow is in development; OIDC, Kubernetes, object storage and MCP are planned; the UI foundation ADR is proposed, not an accepted production design.
- Public sources checked: `erp4us`, `.github`, and `erp4us-org.github.io`. The application repository has existing contribution, conduct, security, governance, ADR, license and agent instructions. GitHub returned no public organization Projects during the review; the site links to the organization’s Projects index, not an invented board.

## GitHub source and refresh

`scripts/github.mjs` lists public organization repositories with REST, then reads issues, pulls, default-branch commits, contributors, milestones and releases from active non-fork public repositories. It uses GraphQL Discussions for repositories with Discussions enabled and includes open, unlocked and unanswered non-announcement topics, plus `type:rfc` and `type:research` issues. Each entry links back to its source. The activity stream shows up to 15 records from the preceding 30 days; accepted ADRs are separately curated source links, not synthetic dated events. Metric definitions, including the limits of the likely-human account heuristic, are in both catalogs and on Development.

Issue eligibility uses existing GitHub labels as the contract. `good first issue`, `help wanted`, `status:ready` or `domain expertise needed` (alias `domain-expertise`) opt an issue in. It must also be open, unassigned and unlocked, without an exclusion such as `status:blocked`, `status:proposed` or `type:epic`. `status:needs-analysis` can signal an open research contribution. Area labels organize eligible work rather than declaring it ready. Existing `area:testing`, `area:infrastructure`, `area:mcp`, `frontend`, `backend`, `architecture`, `accessibility` and `documentation` are mapped along with aliases in the collector. Prefer reusing these labels across repositories to creating parallel names. No labels were changed automatically.

- Local builds read `.cache/github.json` if present. Use `GITHUB_SNAPSHOT=tests/fixtures/github.json npm run build` for deterministic offline QA. With neither file, the site displays a GitHub link and an unavailable state, not zeros. An explicitly selected invalid or missing file fails the build.
- `GITHUB_TOKEN=… npm run github:refresh` uses the API with timeouts and pagination. Do not put a token in a committed file. The cache is written atomically only after every query succeeds and the normalized data passes validation. Restore or reuse this cache for local offline builds when needed.
- The Pages workflow refreshes daily (04:37 UTC), on main pushes and on manual main runs. Credentials are supplied only to the trusted refresh step; PR checks never use the GitHub API. A failed or rate-limited refresh stops before upload, leaving the previous production deployment intact. If the Pages workflow token cannot read cross-repository Discussions, configure repository secret `PUBLIC_GITHUB_READ_TOKEN` with read access only to the public organization data (including Discussions); no token is shipped to browsers. Verify the default token in the first main run before provisioning anything.

## Editorial and launch checklist

- Review the six Markdown files in `src/content/devlog`. Set the publication date and change `draft: true` only after approval. Use explicit locale and slug; translations share a `translationKey` but keep permanent URLs. Markdown accepts fenced code and text diagrams, or local SVG diagrams with alternative text. A post can provide a distinct raster social `image` in `public/`; otherwise it uses the branded 1200×630 default. Update the source alongside any re-render of `public/brand/community-social.svg`.
- Approve the founder text before adding it to the site; the draft was kept out of this public repository. The contributor wall stays hidden until at least two opted-in entries with public evidence are reviewed in `src/content/recognition.json`. A role must be confirmed, not inferred from commit counts.
- Pages reported workflow publishing, no bound custom domain and no enforced HTTPS; public DNS/redirect could not be verified in the task environment. Do not share `erp4us.org` as the canonical site until completing [the cutover runbook](domain.md). The GitHub Pages canonical base remains the default; `SITE_URL` drives canonical URLs, feeds, sitemap and previews together. No external DNS changes were made.
- After merge, confirm the scheduled build has a successful live snapshot. Recheck mobile onboarding and social unfurls against the actual deployment. For launch, link directly to a contribution or an open design question rather than promising production capabilities.

## Verification

The validation sequence in the README checks formatting, both catalogs, the collector, Astro/TypeScript, internal links, canonical and reciprocal language URLs, Open Graph assets, structured data, both RSS feeds, and sitemap coverage. Browser checks expect a local static build served at port 18746, or set `PREVIEW_URL`. Run `node tests/browser.mjs` with Playwright installed in a separate tooling environment (`PLAYWRIGHT_PATH` can point to its module). Optional `CHROME_PATH`, `AXE_PATH` (axe-core script), and `SCREENSHOT_DIR` enable system Chrome, automated WCAG checks and screenshots without changing production dependencies.
